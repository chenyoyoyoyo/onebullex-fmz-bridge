# 08 Pine 相容性與轉換

## 先分清三件事

1. Pine 能編譯、回測或畫出訊號。
2. FMZ 的執行函式庫能把訊號轉成交易所訂單。
3. 訂單真的成交，且交易所持倉與策略狀態一致。

三者不能互相替代。本工具包已驗證的是 **Pine 交易邏輯 → JavaScript 移植 → FMZ 通用協議 → Spartans 真實開平倉**。不是已證明原生 Pine 可以直接下單，也不是所有 Pine 策略都必須在所有 FMZ 交易所上轉成 JavaScript。

## 此通用協議組合實際遇到的問題

2026-10 的測試使用 FMZ 託管者 v3.9.2 與當時的官方 Pine 執行庫。原生 Pine 印出準備下單訊息後，bridge 只收到行情與帳戶查詢，沒有 trade 請求；交易所也沒有新訂單。

對當時核心的本地唯讀檢查與離線重現顯示：

- 通用協議的交易所名稱沒有 `Futures`，執行庫選到現貨分支。
- 現貨買入按 `Balance / 幣價` 限制數量，把數量視為 BTC；bridge 的 amount 卻是整數合約張數。假設餘額60 USDT、BTC價格80000，算出0.00075 BTC，再按0位數精度處理會變0，`Buy` 根本未被呼叫。
- 現貨賣出與持倉追蹤依賴 `Stocks`；通用協議帳戶的現貨欄位不是永續合約持倉，無法據此判斷可平多少空單或多單。

這是當時版本、該協議路徑的觀察，不是對未來所有 FMZ Pine 版本的斷言。若要用新版原生 Pine 或自訂執行庫，重新核對其數量、買賣、持倉及成交處理。不可只修改精度、最小下單量、`Lot` 或 bridge 上限，就宣稱已修復。不要修改 bridge 簽名或偽造現貨餘額作為繞路。

## 建議的移植檢查表

| Pine 特性 | JavaScript 必須明確處理 |
| --- | --- |
| `strategy.entry/close/exit` | 整數張數、淨部位、成交確認、減倉與反手順序 |
| `strategy.position_size` | 實際持倉由 `/v2/position/list` 查詢；PAPER 另有模擬帳本 |
| `strategy.equity` | 分清回測初始資金、合約權益、可用保證金、資金帳戶 |
| `percent_of_equity` | 通常是下單名目金額比例，不是每筆最大虧損或保證金比例 |
| `crossover/crossunder` | 同時使用本根與前一根的價格及門檻；動態門檻不能拿當前值回算上一根 |
| `var`、歷史索引、SMMA/ATR | 初值、遞推、平移、缺失值與重啟狀態一致；SMA ATR 與 Wilder ATR 不可擅換 |
| `request.security`、時區、日界線 | 明確取得哪根已收盤K線；檢查 lookahead、週末與跨日行為 |
| 碎形與 pivot | 等右側K線完成才確認，繪圖回移不等於當時已知道訊號 |
| pyramiding、加倉、反手 | 預設不加碼的策略不能被移植成每次訊號都加一張；反手先歸零 |
| stop/limit、盤中出場 | 保留觸發時機；若改成主機輪詢，說明停機時不再有保護 |
| 成交時點 | 區分收盤計算、下一tick送單、成交價；不得把收盤價假裝成成交價 |

另存前交付完整程式、參數對照與行為差異。使用同一組歷史K線做指標/訊號對照，再跑 PAPER，最後在獲准環境做實際成交驗收。不同交易所的行情與歷史起點可能造成合理差異，不能只比圖形外觀。

## 如何判斷真的跑通

依序核對：訊號時間 → 訂單ID → `Status=1` 且 `DealAmount=Amount` → 成交均價 → 持倉改變 → 平倉訂單與成交 → 淨部位0、未成交單0。印出 `submit`、`SIGNAL` 或圖上的箭頭，都不能單獨作為成交證據。

參考： [FMZ 官方 Pine 核心入口](https://www.fmz.com/strategy/358374)、[TradingView 策略與訂單時序](https://www.tradingview.com/pine-script-docs/concepts/strategies/)。本倉庫不再散布官方核心程式；診斷描述是上述時間的實測結果。
